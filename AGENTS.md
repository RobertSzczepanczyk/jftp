# Repository Guidelines

## Project

Course project for the four-day remote **Codex + GitHub Copilot** training for **Signity**. Use agents to understand and document the legacy JFTP desktop application, then modernize it while preserving existing functionality.

**Chat and user-facing explanations: Polish. Repository documentation: English.** Preserve the application's existing UI languages; this instruction does not add a Polish UI locale.

Work within the phase authorized by the user. Phase gates and the supported toolchain belong in `docs/modernization-plan.md` and `docs/build-and-dependencies.md`, not in this file.

## Project-specific conventions

- `com.myjavaworld.gui`, `util`, and `zip` are in-repository shared code. The custom `com.myjavaworld.gui.SwingWorker` is not the JDK class with the same name; preserve its callback semantics when replacing it.
- FTP API (`ftpapi`) and JavaHelp are external dependencies. `Filter`, `DateFilter`, and `RegexFilter` are imported but absent from repository source; establish artifact ownership before substituting them. Dependency versions belong in the build configuration and dependency documentation.
- `src/main/resources_de/` and `src/main/resources_zh_TW/` are separate locale resource roots. Build source encoding does not establish bundle encoding.
- `src/main/images/` and `src/main/help/` are additional classpath resource roots. Preserve resource paths, bundle keys, and JavaHelp IDs.
- Launchers in `src/main/scripts/` and the descriptor in `src/main/assembly/` jointly define the distribution layout; changes must agree on the application JAR and dependency locations.
- The repository map is generated by `tools/generate_repo_map.mjs`. Its references are heuristic; use it to locate code, then confirm behavior in source. The existing untracked `micro` is outside analysis and must remain untouched.

## Agent workflow and TDD

Delegate repository exploration to **GPT-6 Luna** subagents. Give each a bounded scope, clear ownership, expected evidence, and a common reporting format; coordinate their findings instead of loading the entire codebase into the coordinator's context.

For application fixes and refactoring:

1. Define expected observable behavior and acceptance criteria from the relevant documents before changing code. Separate intended behavior from a suspected legacy defect.
2. Write or extend behavioral tests before production changes. If suitable test infrastructure is absent, establish it as part of the authorized work; do not silently skip coverage.
3. For a bug fix, run the new test and confirm it fails for the intended reason. For a behavior-preserving refactor, first confirm characterization tests pass against the baseline. Compilation or dependency-resolution failure is a blocker, not a successful red test.
4. Implement the smallest justified change, run the affected verification suite, and refactor only while tests stay green.
5. When a regression test fails, investigate changed production code first. Change expectations only with evidence that the test was wrong or an explicit behavior decision; retain equivalent coverage.
6. Exercise the changed workflow in the running desktop application and record the result before declaring runtime work complete.

Use unit tests to isolate the behavior under test. Integration tests should use real filesystem/archive operations and a disposable loopback FTP/FTPS server; fake only external boundaries or controlled failures that cannot be reproduced reliably. End-to-end checks use the real desktop app and fixture stack. Assert resulting data and user-visible state, not merely mock invocation counts.

## Manual desktop QA

Required after every task that affects the running application:

1. Start the app using the verified project procedure and isolated preferences, favorites, files, and certificate stores.
2. Use available native desktop automation, such as computer-use or MCP Computer Commander, to exercise the real Swing flow. Browser-only automation cannot validate this app. If native control is unavailable, arrange human validation and report the pending gate; do not claim a pass.
3. Capture screenshots of touched screens. Exercise the changed success flow and relevant failure/cancel paths, including restart or persistence when affected.
4. Verify displayed data, state/enablement, responsiveness, existing locale rendering, and application errors. Compare against the prior JFTP UI where visual behavior should be preserved.
5. Report steps, outcomes, and screenshot locations in the task summary. Fix observed issues before committing runtime changes.

Documentation-only tasks require documentation checks; map-tooling tasks require mapper checks. Neither requires launching Java merely to verify an unrelated change.

## Commits and completion

- Before a runtime commit, relevant automated checks, startup, and manual desktop QA must pass. Automated end-to-end success alone is insufficient.
- Resolve scope-related errors and new warnings; report existing limitations honestly. A blocked required check means the runtime task is incomplete.
- Keep one logical change per commit. Format: `Area: short summary`, for example `FTP: preserve binary transfer`, `Build: align launch paths`, or `Docs: clarify agent workflow`.
- Do not push to a remote unless the user explicitly asks.
- Use `origin` for the contributor's fork and `upstream` for the original project. Publish authorized changes to `origin`; fetch `upstream` and review differences before integrating them. See the fork workflow in `docs/modernization-plan.md` when configuring remotes or synchronizing with the original project.
- Keep this guidance, affected local instructions, and detailed documentation aligned with relevant changes in the same change. Update phase/verification evidence in the plan; do not present proposals as completed work.
- Regenerate and check the repository map after changes to included files: `node tools/generate_repo_map.mjs`, then `node tools/generate_repo_map.mjs --check`.

A task is complete when its agreed behavior and scope checks pass, required manual QA has evidence, documentation and maps reflect the result, and the change is in a consistent, reviewable state. Commit only verified work under the authorized workflow.
